# Reviewnote 학습현황 시각화 개선 조사

이 문서는 "나의 학습현황"(통계) 화면의 시각화 개편을 위해 4개 worker가 서로의 결과를
보지 않고 독립적으로 조사한 뒤 교차검증한 결과를 정리한다. 이번 라운드에서 실제로
구현/배포한 것은 기본 기간을 "최근 30일"로 바꾸는 것 하나뿐이며, 시각화 구조 자체의
재설계는 이 문서를 검토한 뒤 다음 작업에서 진행한다(§14 참고).

## 1. 현재 UI 문제 요약

- 기본 기간이 "전체"라 최근 취약점을 바로 보기 어려웠다(이번 PR에서 '30'으로 수정,
  §14 참고).
- 단원 × 실수유형 매트릭스가 과목별 아코디언(기본 펼침) 안에 5열 버블 그리드로 표시되어
  모바일 세로 스크롤이 매우 길다.
- 버블 크기(12~28px)+색상(에메랄드→노랑→주황→로즈)의 이중 인코딩이 직관적이지 않고,
  터치 기기에서는 hover 전용 툴팁이라 정확한 횟수를 확인할 수 없다.
- "가장 약한 게 뭔지"를 바로 답해주는 요소("취약 단원 TOP 5")가 화면 맨 아래, 전체
  매트릭스를 다 지나야 나온다 — 우선순위가 화면 순서와 반대다.

## 2. 현재 데이터 구조/제약

`src/App.tsx`(별도 컴포넌트 파일 없음, `activeTab==='stats'` 블록에 인라인):

- `filteredMistakesForStats`(1342행) — admin은 전체/선택 학생, 학생은 본인만; 기간
  필터는 `all`이면 무필터, `90`/`30`이면 `m.date >= (오늘-N일)` 비교.
- `stats`(1368행) — `gradeCounts`/`chapterCounts`/`causeCounts`/`totalGrade`/
  `totalCause`/`topChapters`(카운트 내림차순 top 5, **이미 계산되어 있음**).
- `bubbleChartData`(1391행) — grade → chapter → `ROOT_CAUSE_OPTIONS`(5종 고정: 🧮계산
  실수/📘공식오적용/🔍문제오독/🧠개념부족/🎯풀이전략실패) count 매트릭스.
- **핵심 제약**: Reviewnote는 학생이 "등록한 오답"만 기록하는 시스템이다. 전체 풀이
  문제 수(분모)가 없으므로 정답률/오답률/전체 대비 비율을 계산할 방법이 없다. 지금
  믿을 수 있는 유일한 값은 **"등록된 오답 안에서의 상대적 집중(raw count)"** 뿐이다.
- 추가 데이터 특성(기존 감사 확인, 이번에 재확인): `chapter`는 AI 자유 텍스트 분류라
  근소하게 다른 표기가 다른 단원처럼 쪼개질 위험이 있음; `rootCauses`는 학생
  self-report(다중 선택)이라 교사/AI 검증이 아님; `stageType`/`needsHelp`는
  `stats`/`bubbleChartData` 어디에도 쓰이지 않아 현재도 광범위 통계에서 배제돼 있음;
  `reviews`는 O/X/★ 3칸의 **현재 상태 snapshot**일 뿐 시계열 로그가 아님; 체크리스트
  progressive-disclosure 데이터는 아직 신규라 대부분의 기존 레코드에는 없음.

## 3. 최근 30일 default가 적합한 이유

`statsPeriodFilter`는 어디에도 저장되지 않는 plain `useState`라(§확인됨) 매 진입마다
초기값으로 시작한다. "최근 시험대비/최근 취약점"이 학생·교사 모두에게 더 실행 가능한
기본 관점이고, "전체 누적"은 장기 추이 참고용으로 남겨도 손해가 없다(토글로 언제든
전환 가능). 이 부분은 이미 구현/배포 완료했다(§14).

## 4. Worker A 결과 — 교육 데이터 관점

11개 후보를 "3초 안에 약점을 알아보는가" 기준으로 순위화. 상위: **TOP 3 카드**(비교
작업 자체가 필요 없음) > **ranked list** > **horizontal bar**(길이 인코딩이 인간이
가장 정확히 읽는 방식, Cleveland & McGill 서열과 일치) > mistake-type chips(보조용) >
chapter accordion(네비게이션 셸로만 유효, 1차 신호로는 부적합) > sparkline(2차 뷰) >
small multiples > stacked bar(교차비교 약함) > heatmap > **현재 bubble matrix**(area+
color 이중 인코딩이 area 단일보다도 나쁨, 정보 이득 없이 인지 비용만 추가) > **radar
(최하위)**.

Radar 검토: 각도/면적 비교는 위치/길이 비교보다 구조적으로 부정확하고, 5개 원인
카테고리가 "하나의 프로필"로 읽을 만한 다차원 실체가 아니라 독립적인 5개 카운트일
뿐이라 폴리곤 모양이 실제 진단 가치를 주지 않는다. 0값 축이 중심점으로 붕괴되며
"균형잡힌 것처럼" 보이는 착시를 유발해 이 앱이 가장 피해야 할 실수(0을 "확인된 강점"과
혼동)를 정확히 재현한다. **결론: REJECT**.

저-N(소량 데이터) 처리: 숨기지 말고, N<3 정도의 셀/바는 옅은 채도·해칭 등으로
구분하고 원시 카운트("3건")를 항상 병기해 "확신도 낮음"을 시각적으로 전달할 것 —
비율/등급을 계산해서 보여주지 말 것.

흥미로운 발견: `stats.topChapters`가 이미 계산돼 있는데도 화면 맨 아래, 요약이 아니라
"보충 정보"처럼 배치돼 있다 — 인프라는 이미 있고 배치 순서만 잘못됐다.

## 5. Worker B 결과 — 모바일 UX 관점 (390px)

실제 코드(`App.tsx:1817-2021`)를 직접 읽고 분류:

| 요소 | 분류 | 이유 |
|---|---|---|
| 과목(grade) 아코디언 wrapper | DRILLDOWN | 기본이 펼침(`!== false`)이라 실제로는 스크롤을 전혀 줄이지 못함 — 기본 접힘으로 |
| 아코디언마다 반복되는 5열 헤더 | REMOVE | 완전한 중복, 전역 1회로 통합하거나 구조 변경 시 제거 |
| 버블 그리드 자체 | REPLACE | area+color 이중 인코딩보다 bar 길이가 더 빠르게 읽힘 |
| hover 전용 카운트 툴팁 | REMOVE(현행) | 터치 기기에서 hover가 발동하지 않아 숫자가 실질적으로 안 보임 |
| 하단 low→high 범례 | COMPACT/REMOVE-if-redesigned | 인코딩을 단순화하면 범례 자체가 불필요해짐 |
| "취약 단원 TOP 5" | KEEP, MOVE UP | 페이지에서 가장 3초-친화적인 요소인데 맨 아래 묻혀 있음 |
| 기간 토글 탭 | KEEP | 작고 명확, 30일 default와 시너지 |
| 관리자 학생 선택 | COMPACT | 드롭다운 하나에 큰 카드(~90px) 낭비, 인라인 압축 가능 |

핵심 답변: 첫 화면(스크롤 없이)엔 제목+기간토글+(admin만)학생선택+**TOP 3**만 보여야
한다; 상세 매트릭스는 기본 접힘/on-demand여야 한다; TOP 3가 매트릭스보다 먼저 나와야
한다; accordion은 기본 펼침·subject 단위로는 friction만 추가(2단계 구조 필요); bar/list가
table보다 낫다(길이 인코딩 + 실제 44px 터치 타겟 확보 가능 — **현재 버블은 12~28px로
Apple/Google 최소 터치 타겟 기준(44px) 자체를 위반하는 실질적 버그**); radar는 5개
한글 라벨이 390px에서 겹치거나 잘리고 작은 차이가 안 보여 REJECT; 가로 스크롤은
TOP3 칩 정도의 보조 용도 외엔 정보를 숨기는 역효과.

예상 절감: 현재 과목당 매트릭스 섹션 ~450-480px × 2-3과목 + TOP5 카드(~380px) ≈
**1300-2300px**(뷰포트 2-3배) → 재설계 첫 화면(제목+토글+admin행+TOP3) ≈
**350-400px**, 약 **70-80% 감소**.

추가 발견: `max-w-[360px] mx-auto`가 모든 폰 폭에서 인위적으로 좁힘; 버블 크기/색이
데이터셋 전체 최댓값(`maxCountInBubbles`) 대비 상대 비율이라 카운트 1~2건짜리
단원도 "크고 빨간" 버블로 보일 수 있음(확신도 왜곡, Worker A/D와 독립적으로 수렴);
5열 40px 헤더에 맞추려 emoji를 정규식으로 제거하는 코드는 매트릭스 형식이 콘텐츠와
싸우고 있다는 증상.

## 6. Worker C 결과 — 시각화 방식 비교

8개 후보(A~H)를 glanceability/세로길이/밀도/우선순위 표현력/학생·교사 친화성/구현
난이도/오도 위험으로 비교(표는 원본 조사 참고, 핵심만 요약):

- **D(TOP-N ranked list)** 1위 — `stats.topChapters`가 이미 존재, `causeCounts`용
  동일 로직 하나만 추가하면 됨. 가장 짧고, 가장 정직하고, 가장 빠르게 읽힘.
- **G(summary cards + drilldown)** 2위 — D를 카드로 감싸고 상세는 매트릭스/히트맵을
  tap-to-expand로 유지. 2단 구조가 "요약 먼저, 상세는 필요할 때"를 정확히 구현.
- **B(horizontal bar, chapter-ranked)** 3위 — 리스트보다 약간 느리지만 "차트"를
  기대하는 사용자에게도 익숙하고, 정렬 자체가 우선순위를 표현.
- **C(stacked bar)는 명시적으로 배제** — `rootCauses`가 다중 선택이라 한 오답이 여러
  원인에 동시에 카운트되므로 100%-stacked 형태로 그리면 세그먼트 합이 전체와 맞지
  않는 **정합성 함정**이 생긴다(Worker D도 독립적으로 동일 결론).
- E(heatmap)/F(accordion+mini chart)는 A(현재 버블)보다는 낫지만 D/G/B보다 우선순위
  표현력이 약함 — 상세 뷰 후보로는 유효.
- H(sparkline)는 우선순위 축과 무관한 보조 지표(추세)로만 유효.

Radar 검토(독립): 위치/길이 비교가 각도/면적 비교보다 정확하다는 지각 연구, 이 앱의
실제 데이터 볼륨(30일 창에 카테고리당 0~5건 수준)에서는 작은 차이가 폴리곤 왜곡으로
거의 안 보임, 0값 축이 폴리곤 전체를 "괜찮아 보이게" 왜곡, 5개 한글 라벨의 모바일
공간 문제, "삐죽한 모양=전체적으로 못한다"는 오독 위험. **결론: REJECT(단정적)**.

## 7. Worker D 결과 — Reviewnote 데이터 제약 기반 검토

코드 확인: `stats`/`bubbleChartData` 어디에도 `stageType`/`needsHelp`가 쓰이지 않음
(이미 광범위 통계에서 배제돼 있음 — 재설계에서도 이 두 필드를 새 차원으로 쓰지 말 것).
`chapter` 정확 문자열 매칭이라(fuzzy merge 없음) 근소 표기 차이가 쪼개질 수 있음 —
해결은 스키마/로직 변경이 아니라 **"상위 N개만 보여주기"라는 표현 절제**로 완화.

8개 후보의 오도 위험표(요약): A(현재 버블)/E(heatmap)는 중간 위험(원시 카운트만
표시, 전체 단원을 다 보여주지 않고 상위 N만); B(bar)/D(list)/G(cards)는 낮은
위험(카운트 그대로, "건" 단위); **C(stacked bar)는 높은 위험**(위 정합성 함정,
독립적으로 동일 결론); **H(sparkline)는 잘못 쓰면 높은 위험** — `reviews`는 시계열
로그가 아니라 현재 상태 snapshot뿐이므로, sparkline은 반드시 `date`(등록일, 실제
시계열 데이터) 기반 "등록 건수 추이"로만 그려야 하고 `reviews`에서 "복습 성공률
추이"를 파생시키면 존재하지 않는 이력을 만들어내는 것.

라벨링 규칙(권장): "%"/"율"/"정답률"/"오답률" 사용 금지, 모든 카운트는 "건" 단위로
표기; 화면 상단에 "등록된 오답 {N}건 중" 한 줄로 범위를 명시(위젯마다 반복 disclaimer
불필요, 한 번이면 충분); N<3인 항목은 채도를 낮추거나 outline 스타일로 구분하되
숫자는 항상 노출; `rootCauses`는 "학생이 스스로 체크한"이라는 self-report 프레이밍을
화면에서 처음 언급할 때 한 번 명시.

구현 가능성: `stats.topChapters`는 이미 재사용 가능; `causeCounts`용 top-N은
`Object.entries().sort().slice()` 한 줄 추가로 충분(신규 aggregation 아님, 순수
presentation 파생값); `bubbleChartData`는 A/E/F/G의 detail view에 그대로 재사용
가능 — 즉 재설계는 **렌더링 레이어 변경**이며 새 파이프라인이 필요 없음.

## 8. 교차검증 결과

4개 worker가 서로의 결과를 보지 않고도 강하게 수렴한 지점:

1. **Radar chart는 전원 일치로 REJECT** — 위치/길이 vs 면적/각도의 지각 정확도 차이,
   0값 축의 왜곡, 5개 한글 라벨의 모바일 공간 문제, 오독 위험까지 근거가 거의
   동일하게 겹친다. 예쁘다는 이유로 채택할 근거가 전혀 없다.
2. **"요약 먼저(SUMMARY FIRST), 상세는 필요할 때(DETAIL ON DEMAND)"** — Worker A(top3
   카드 1위), B(TOP3가 매트릭스보다 먼저 나와야 함), C(D/G가 1·2위), D(topChapters
   재사용, 낮은 구현 난이도)가 각자 다른 각도에서 동일한 구조로 수렴했고, 이는
   사용자가 §10에서 제시한 "권장 구조"와도 독립적으로 일치한다.
3. **현재 버블 매트릭스는 최하위권** — area+color 이중 인코딩(A), 44px 터치 타겟
   위반(B), 낮은 glanceability·우선순위 표현력(C), 저-N 확신도 왜곡(A·B·D 공통) 등
   4개 관점에서 각각 독립적으로 약점이 지적됐다.
4. **Stacked bar(다중선택 100%-stack)는 유일하게 "정합성 함정"으로 명시적 배제** —
   Worker C와 D가 서로 다른 이유로 조사했지만 동일한 결론(`rootCauses` 다중 선택이라
   세그먼트 합이 전체와 안 맞음)에 도달했다.
5. **Sparkline/추세는 2차 지표로만 유효, `reviews` 기반은 금지** — A("2차 뷰"),
   C("우선순위와 무관한 보조 지표"), D(`reviews`는 시계열 로그가 아니므로 `date` 기반
   등록 건수 추이로만 한정)가 같은 결론에 각자 도달했다.
6. **저-N 처리 방식이 A와 D에서 거의 동일하게 도출** — 숨기지 않고 옅은 채도/해칭
   + 원시 카운트 병기, 비율/등급 계산 금지.
7. **구현 난이도가 낮다는 점도 C와 D가 독립적으로 확인** — `stats.topChapters`가
   이미 있고, `bubbleChartData`가 detail view에 그대로 재사용 가능해 순수
   렌더링 레이어 변경이면 충분.

## 11. 추천안 2위 — MVP: 순수 TOP-N 리스트 + 기존 매트릭스 drilldown

카드/바 없이 `topChapters`+신규 `topCauses` 두 리스트만 최상단에 배치하고, 현재
버블 매트릭스는 코드 변경 없이 "상세 보기" 토글 뒤로 접기만 한다. 코드 변경 범위가
가장 작고(신규 파생값 1개 + 접기 토글 상태 1개), 3초 판독 문제를 즉시 해결하면서
매트릭스 재설계는 완전히 다음으로 미룰 수 있는 안전한 중간 단계.

## 12. 추천안 3위 — 상세 뷰(detail-only)로서의 매트릭스 개선

구조는 유지하되(과목별 그룹, 단원×원인 카운트) 상세 뷰 전용으로 격하하고: (a) 기본
접힘, (b) 버블(area+color) → 고정 크기 셀+in-cell 숫자로 단순화(터치 타겟도 자연히
개선), (c) 반복되는 5열 헤더를 그룹당 1회로 통합, (d) count=0인 단원/원인 조합은
숫자만 흐리게. 1·2위보다 구조 변경이 커서 3위로 두지만, "완전히 새로운 화면을 만들
여유가 없을 때"의 현실적 대안.

## 13. 추천하지 않는 방식

- **Radar/spider chart** — §8-1 참고, 4개 worker 전원 일치 REJECT.
- **100%-stacked bar(실수유형 구성비)** — `rootCauses` 다중 선택으로 세그먼트 합이
  전체와 안 맞는 정합성 함정, Worker C·D 독립적으로 배제.
- **`reviews` snapshot 기반 "복습 성공률 추이" 라인 차트** — 시계열 로그가 존재하지
  않는 데이터를 만들어내는 것과 같음.
- **정답률/오답률/전체 문제 대비 비율 표시** — 분모 자체가 없음(§2).
- **현재처럼 아코디언 기본 펼침 + 전체 매트릭스 즉시 노출** — 3초 판독을 구조적으로
  방해하는 현재의 핵심 실패 패턴.

## 18. 구현 난이도

- **추천안 1위/2위**: 낮음. `stats.topChapters`는 이미 존재, `causeCounts`용 top-N은
  1줄 추가(`Object.entries().sort().slice()`), 아코디언 기본값 `false`로 변경, 신규
  접기 토글 상태 1개. `filteredMistakesForStats`/`stats`/`bubbleChartData`의
  aggregation semantics는 전혀 건드리지 않음(순수 렌더링 레이어).
- **추천안 3위**: 낮음-중간. 버블 → 고정 셀+숫자 렌더링 교체, 헤더 통합 리팩터가
  필요해 1위/2위보다 diff가 조금 더 크다.

## 19. Regression risk

- schema/DB 변경 없음, `root_causes`/`review` 데이터 의미 변경 없음 — 낮음.
- 가장 큰 리스크는 **범위 확장 유혹**: 라벨링 규칙(§7 D)을 지키지 않고 "%"/"율"을
  넣거나, `reviews`에서 추세를 파생시키는 것 — 구현 시 명시적으로 가드해야 함.
- 학생/관리자 parity — 현재도 role 구분 없이 같은 화면(admin만 학생 선택 추가)이므로
  재설계 시에도 새로운 role gating을 추가하지 않아야 함.
- 이 화면은 현재 앱 전역의 `rn-*` 디자인 시스템 클래스를 쓰지 않는 원시 Tailwind
  구현이라(다른 화면들은 이미 마이그레이션됨), 재설계 시 새 CSS를 어느 체계로 쓸지
  결정 필요 — 위험은 아니지만 다음 작업 스코프에 포함해 판단할 사항.

## 20. 최종 추천

**추천안 1위(SUMMARY FIRST: TOP3 카드 → 실수유형 compact bar → 단원 상세
drilldown)**를 다음 작업에서 별도 PR로 구현. 근거: 4개 worker가 독립적으로 동일
구조에 수렴했고, 기존 데이터(`stats.topChapters`, `causeCounts`)로 대부분 구현
가능해 구현 난이도가 낮으며, radar/stacked-bar/reviews-기반-추세 등 명확한 오도
위험이 있는 후보들을 배제한 상태로 남는다. 라벨링은 Worker D의 규칙(건수만 표기,
"%"/"율" 금지, 저-N은 옅게+숫자 병기, "등록된 오답 N건 중" 범위 고지 한 줄)을
그대로 채택한다. Radar chart와 100%-stacked bar는 이번 조사에서 명확히 근거를
갖고 배제되었으므로 향후에도 재검토 없이 제외한다.
